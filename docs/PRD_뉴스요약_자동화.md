## 1. 개요

### 1.1 제품 한 줄 정의
매일 정해진 시각에 기술 뉴스 RSS를 자동 수집하여, 사전 정의된 주제에 해당하는 기사 1건을 생성형 AI로 3줄 요약한 뒤 Notion 데이터베이스에 자동 저장하는 무인 자동화 시스템.

### 1.2 배경
기술 뉴스는 매일 다량으로 쏟아지지만 전부 읽는 것은 비효율적이다. 사람이 개입하지 않고도 "관심 주제의 오늘자 핵심 기사 1건 + 3줄 요약"이 매일 아카이브되는 파이프라인을 구축한다.

### 1.3 문제 정의
| 문제 | 해결 방향 |
|---|---|
| 뉴스 양이 많아 선별에 시간이 든다 | 키워드 기반 자동 필터링 |
| 기사 전문을 읽어야 내용 파악이 된다 | 생성형 AI로 3줄 요약 자동 생성 |
| 읽은 뉴스가 축적되지 않는다 | Notion DB에 구조화 저장 |
| 수동 실행은 지속되지 않는다 | 스케줄 트리거로 무인 자동 실행 |

## 2. 목표 및 성공 기준

### 2.1 제품 목표
- G1. 사람의 개입 없이 매일 자동으로 뉴스 1건이 수집·요약·저장된다.
- G2. 동일 기사가 중복 저장되지 않는다.
- G3. 오류가 발생해도 시스템이 멈추거나 비용이 폭증하지 않는다.

### 2.2 학습 목표 (과제 요건)
- L1. RSS 수집 → AI 가공 → 저장으로 이어지는 자동화 워크플로우를 설명할 수 있다.
- L2. 생성형 AI로 텍스트 요약을 자동화하는 방법을 설명할 수 있다.
- L3. 스케줄 트리거와 에러 처리를 포함한 안정적 자동화 설계 원리를 설명할 수 있다.

### 2.3 성공 기준 (측정 가능)
| ID | 기준 | 측정 방법 |
|---|---|---|
| S1 | 연속 7일간 수동 개입 없이 자동 실행 성공 | Notion DB에 7건(또는 정상 스킵 로그) 확인 |
| S2 | 4개 필수 속성 매핑 정확도 100% | 저장된 레코드 전수 검수 |
| S3 | 중복 저장 0건 | 중복방지키 기준 유니크 검증 |
| S4 | 요약 호출 기사 1건당 1회 준수 | 실행 로그의 AI 모듈 호출 횟수 확인 |
| S5 | 월 API 비용 0원 | Gemini 프로젝트 결제 비활성 상태 유지 |
| S6 | 팀원 전원이 자기 담당 모듈을 설명 가능 | 내부 시연/발표 |

## 3. 범위

### 3.1 In Scope
- 스케줄 기반 자동 트리거 (1일 1회)
- RSS 피드 수집 및 파싱
- 키워드 기반 주제 필터링 및 1건 선별
- 중복 저장 방지
- 생성형 AI 3줄 요약
- Notion DB 자동 저장
- 재시도 및 에러 처리
- 산출물 문서화 (워크플로우 설명 문서, README)

### 3.2 Out of Scope
- 사용자 로그인 / 웹 UI 개발
- RSS 미제공 사이트 크롤링 **(과제 금지사항)**
- 다국어 번역
- 실시간(분 단위) 뉴스 수집
- 하루 다건 수집 (v1은 1일 1건 고정)

### 3.3 보너스 (선택, v1.1)
- B1. 썸네일 이미지 자동 생성
- B2. 감성 분석 태그 (긍정/중립/부정)

## 5. 시스템 아키텍처

### 5.1 전체 흐름

```
[1] 스케줄 트리거
    매일 09:00 (Asia/Seoul)
         ↓
[2] RSS 수집
    지정 RSS 피드에서 최신 항목 N건 조회
         ↓
[3] 주제 필터링
    키워드 매칭 → 조건 만족 항목만 통과
         ↓
[3-1] 후보 집계
    통과분을 배열 1건으로 모으고 그중 최신 1건 선택
         ↓
    ├─ 매칭 0건 → [정상 스킵] 로그 기록 후 종료
         ↓
[4] 중복 체크
    Notion DB에서 중복방지키 조회
         ↓
[4-1] 조회 결과 집계
    조회 결과를 배열 1건으로 모음
         ↓
    ├─ 이미 존재 → [정상 스킵] 종료 (AI 호출 안 함)
         ↓
[5] AI 요약
    Gemini API 호출 (기사당 1회) → 3줄 요약 생성
         ↓
[6] Notion 저장
    제목 / 요약문 / 원문 링크 / 발행일시 속성 매핑 저장
         ↓
[7] 종료 로그 기록
```

### 5.2 설계 원칙
1. **중복 체크를 AI 호출보다 앞에 배치** — 불필요한 API 호출을 원천 차단하여 한도와 비용을 방어한다.
2. **정상 스킵과 오류를 구분** — 매칭 기사 0건은 실패가 아니다. 알림 피로도를 줄이고 실제 장애만 드러나게 한다.
3. **재시도 상한 고정** — 모든 재시도는 최대 2회. 무한 루프 및 비용 폭증 방지.
4. **단방향 파이프라인** — 시나리오가 자기 자신을 다시 트리거하는 구조를 만들지 않는다.
5. **"0건"을 감지 가능한 형태로 만든다** — [3-1], [4-1]의 집계 단계가 여기에 해당한다.

> **[3-1], [4-1]이 필요한 이유 (v1.1 추가)**
> Make에서 Filter나 검색 모듈의 결과가 0건이면 **뒤따르는 모듈이 아예 실행되지 않고 흐름이 그대로 끝난다.**
> 즉 "매칭 0건이면 로그를 남기고 종료"(E-03)나 "중복이 없으면 계속 진행"(E-04)을 표현할 방법이 사라진다.
> Array aggregator는 입력이 0건이어도 **빈 배열 1건을 반드시 내보내므로**, 이 단계를 끼워야
> 뒤에서 `length(array)`로 0건 여부를 판정할 수 있다. 초안 흐름도에는 이 단계가 빠져 있었다.

## 6. 기능 요구사항

### FR-01. 스케줄 트리거
| 항목 | 내용 |
|---|---|
| 설명 | 매일 지정된 시각에 워크플로우를 자동 실행한다 |
| 실행 시각 | 매일 09:00, 타임존 Asia/Seoul |
| 실행 빈도 | 1일 1회 (반복/루프 트리거 금지) |
| 수용 기준 | 수동 실행 없이 3일 연속 지정 시각 ±5분 내 실행 로그 존재 |

### FR-02. RSS 수집
| 항목 | 내용 |
|---|---|
| 설명 | 지정된 RSS 피드에서 최신 기사 목록을 가져온다 |
| 수집 건수 | 회당 최대 20건 조회 (필터링 대상 풀) |
| 추출 필드 | title, link, pubDate, description(또는 content), guid |
| 제약 | RSS 미제공 사이트 크롤링 금지 |
| 수용 기준 | 5개 필드가 누락 없이 다음 단계로 전달됨 |

**RSS 피드 후보 → 확정 (O1 종료, 2026-07-29)**

| 피드 | 성격 | 초안 | 확정 | 실측 결과 |
|---|---|---|---|---|
| ZDNet Korea | 국내 IT 전문지 | 1순위 | **제외** | `news_xml.asp` → HTTP 404 |
| 전자신문 | 국내 IT/산업 | 2순위 | **1순위** | guid 20/20, description 248자, 날짜 변환 실패 0 |
| Google News RSS (키워드 지정) | 키워드 사전 필터 가능 | 백업 | 백업 | guid 20/20이나 description 41자로 요약 부적합 |

> 선정 시 확인 항목: ① RSS 주소가 실제 동작하는가 ② 본문(description) 길이가 요약에 충분한가 ③ pubDate 포맷이 파싱 가능한가
>
> 위 확인은 `cd prototype && python check_feed.py` 로 재현할 수 있다(외부 호출은 피드 조회뿐, 크레딧 0).

### FR-03. 주제 필터링
| 항목 | 내용 |
|---|---|
| 설명 | 사전 정의 키워드에 해당하는 기사 1건을 선별한다 |
| 매칭 대상 | 제목 우선, 미매칭 시 본문 요약(description) |
| 선택 규칙 | 복수 매칭 시 pubDate가 가장 최신인 1건 |
| 수용 기준 | 매칭 결과가 정확히 0건 또는 1건으로 확정됨 |

**키워드 정책**

```
1순위 (제목 매칭): AI, 인공지능, LLM, 생성형, ChatGPT, Gemini, Claude
2순위 (본문 매칭, 1순위 실패 시): 머신러닝, 딥러닝, 반도체, GPU, 데이터센터
제외 (매칭 시 후보에서 배제): 광고, 협찬, 이벤트, 채용, 프로모션
```

| 정책 | 선택 이유 |
|---|---|
| 1순위는 제목만 매칭 | 제목에 키워드가 있으면 기사 주제일 확률이 높아 정확도가 확보된다 |
| 2순위를 fallback으로 운영 | 1순위만 쓰면 수집 실패일이 잦아져 시스템이 무의미해진다 |
| 제외 키워드 운영 | 홍보성 기사가 선택되면 요약 품질이 떨어지고 API 호출이 낭비된다 |
| 최신 1건 선택 | "오늘의 뉴스" 성격에 부합하며 선택 기준이 결정론적이라 재현 가능하다 |

**⚠️ Make 구현 제약 및 v1 단순화 (v1.1 추가)**

위 2단계 fallback("1순위가 0건일 때만 2순위")은 **Make에서 그대로 구현되지 않는다.**
Make의 Filter는 번들을 하나씩 통과시키는 구조이고, "전체를 다 훑고 난 뒤 1순위가 하나도 없었는지"는
모든 번들이 지나간 뒤에야 알 수 있다. 정석대로 하려면 집계를 한 겹 더 쌓고 Router로 갈라야 하는데,
모듈 수·크레딧·디버깅 난이도가 모두 올라간다.

| | v1 (채택) | 정석 2단계 |
|---|---|---|
| 구현 | 1·2순위를 **OR로 합친 단일 Filter** | Aggregator 2겹 + Router |
| 모듈 수 | 12개 | 16개 이상 |
| 결과 차이 | 1순위 기사가 있는 날에도 2순위 기사가 더 최신이면 그쪽이 선택될 수 있음 | 항상 1순위 우선 |

두 키워드군 모두 팀이 정한 관심 주제이므로 v1의 결과 차이는 수용 가능하다고 판단한다.
정석 2단계는 v1.1 이후 과제로 남긴다.

- Make 구현: `docs/make-시나리오-명세.md` [3]번 모듈
- 참조 구현(`prototype/article_filter.py`)은 **정석 2단계로 구현되어 있다.** 의도된 차이이며,
  단계별 로직을 문서화·설명하기 위한 기준 구현으로 쓴다.

### FR-04. 중복 저장 방지
| 항목 | 내용 |
|---|---|
| 설명 | 이미 저장된 기사는 재저장하지 않는다 |
| 중복방지키 | RSS `guid` 1순위, 없으면 원문 링크 문자열 |
| 검사 위치 | **AI 요약 호출 이전** |
| 동작 | 키 일치 레코드 존재 시 정상 스킵 후 종료 |
| 수용 기준 | 동일 기사로 워크플로우를 2회 실행해도 레코드가 1건만 존재 |

### FR-05. AI 요약
| 항목 | 내용 |
|---|---|
| 설명 | 기사 내용을 3줄 이내로 요약한다 |
| 사용 모델 | Google Gemini (무료 티어, Flash 계열 권장) |
| 호출 횟수 | 기사 1건당 정확히 1회 (재시도 제외) |
| 출력 형식 | 불릿 3줄, 각 줄 60자 이내 |
| 수용 기준 | 3줄 초과 출력 0건, 요약문이 원문 주제와 일치 |

**요약 프롬프트 명세**

```
너는 기술 뉴스를 요약하는 편집자야.
아래 기사를 정확히 3줄 이내로 요약해줘.

규칙:
- 각 줄은 "- "로 시작하는 불릿 형태
- 각 줄 60자 이내
- 사실만 전달하고 추측이나 의견을 넣지 말 것
- 기사에 없는 내용을 만들어내지 말 것
- 요약 외의 머리말, 맺음말, 설명은 출력하지 말 것

제목: {{title}}
본문: {{content}}
```

> 프롬프트는 개발 중 개선될 수 있으며, 초안→수정→최종 이력을 README에 기록한다.

### FR-06. Notion 자동 저장
| 항목 | 내용 |
|---|---|
| 설명 | 요약 결과를 Notion DB에 속성별로 저장한다 |
| 저장 방식 | 신규 페이지(행) 생성 |
| 수용 기준 | 4개 필수 속성이 각각 올바른 타입으로 저장됨 |

### FR-07. 에러 처리
| 항목 | 내용 |
|---|---|
| 설명 | 오류 발생 시 재시도 후 안전하게 종료한다 |
| 재시도 상한 | 단계별 최대 2회 |
| 수용 기준 | 강제 오류 주입 테스트에서 시나리오가 무한 반복 없이 종료됨 |

상세 정책은 10장 참조.

## 7. 데이터 모델 — Notion DB 스키마

**DB 명**: `기술 뉴스 아카이브`

| 속성명 | 타입 | 필수 | 매핑 소스 | 비고 |
|---|---|---|---|---|
| 제목 | Title | ✅ | RSS `title` | |
| 요약문 | Text | ✅ | Gemini 응답 | 불릿 3줄 |
| 원문 링크 | URL | ✅ | RSS `link` | |
| 발행일시 | Date | ✅ | RSS `pubDate` | ISO 8601 변환 필요 |
| 출처 | Select | ⬜ | 피드명 상수 | |
| 중복방지키 | Text | ⬜ | `guid` 또는 링크 | 조회 대상 |
| 수집일시 | Date | ⬜ | 실행 시각 | |
| 감성 | Select | ⬜ | (보너스 B2) | 긍정/중립/부정 |
| 썸네일 | Files | ⬜ | (보너스 B1) | |

**저장 예시**

```
제목:      AI 에이전트의 미래와 전망
요약문:    - 최신 AI 에이전트는 자율적 의사결정 능력이 강화되고 있음
           - 기업 생산성 도구와의 결합 사례가 급증하는 추세임
           - 보안 및 윤리 가이드라인의 필요성이 대두됨
원문 링크: https://example.com/news/123
발행일시:  2026-07-27 08:30
출처:      전자신문
```

**⚠️ 날짜 변환 주의**: RSS의 `pubDate`는 RFC 822 형식(`Mon, 27 Jul 2026 08:30:00 +0900`)인 경우가 많다. Notion Date 속성은 ISO 8601을 요구하므로 중간에 포맷 변환 단계가 필요하다. **개발 중 가장 흔한 실패 지점이므로 우선 검증할 것.**

## 8. 기술 스택

| 구분 | 선택 | 근거 |
|---|---|---|
| 자동화 툴 | **Make** | 시각적 빌더로 코딩 무경험 팀원의 진입장벽이 가장 낮음 |
| 생성형 AI | **Google Gemini API (무료 티어)** | 신용카드 없이 사용 가능, 본 프로젝트 사용량 대비 한도가 충분 |
| 저장소 | **Notion** | 과제 권장 도구, 팀 무료 플랜으로 충분 |
| 문서 | Notion / GitHub README | |

### 8.1 Make 무료 플랜 제약 및 대응

<cite index="34-1">Make 무료 플랜은 월 1,000 크레딧, 활성 시나리오 2개, 최소 15분 스케줄 간격을 제공한다.</cite>

| 제약 | 본 프로젝트 영향 | 대응 |
|---|---|---|
| 월 1,000 크레딧 | 실행당 약 **10~14 ops** × 30일 ≈ **300~420 ops** → 여유 있음 | 개발 중 테스트는 참조 구현(`--dry-run`)으로 대체해 크레딧을 아낀다 |
| 활성 시나리오 2개 | 메인 1개 + (선택)알림 1개 = 정확히 한도 | 에러 알림을 별도 시나리오로 빼지 말고 메인 안에 포함시킬 것 |
| 최소 15분 간격 | 1일 1회 실행이므로 무관 | — |

> **추정치 정정 (v1.1)**: 초안의 "실행당 6~8"은 과소평가였다. 실제 구성은 모듈 12개이며,
> 0건 감지를 위한 집계 단계([3-1], [4-1])와 변수 설정 모듈이 추가로 소모된다.
> 정상 저장되는 날은 약 10~14 ops, 정상 스킵되는 날은 약 4~6 ops로 잡는다.
> 한도 대비 여유는 여전하지만 **테스트 실행분의 여유가 초안 추정보다 좁다**는 점이 달라진다.

> <cite index="33-1">AI 관련 기능은 일반 모듈과 크레딧 소모 방식이 다를 수 있으므로</cite> 개발 초기에 1회 실행당 실제 소모량을 로그로 확인한다. M1 첫 주에 실측해 위 표를 확정할 것.

### 8.2 Gemini 무료 티어 제약 및 대응

<cite index="26-1">Gemini 무료 티어는 신용카드 없이 사용 가능하며, 모델에 따라 분당 5~15회, 일 100~1,000회 수준의 호출 한도를 가진다.</cite> 본 프로젝트는 **1일 1회 호출**이므로 한도에 여유가 매우 크다.

> **실측 정정 (v1.2, 2026-08-03)** — 초안의 "일 100~1,000회"는 실제와 다르다.
> AI Studio > 비율 제한에서 확인한 본 프로젝트 계정의 실제 한도는 **RPM 5 / RPD 20**이다
> (PRD R2가 경고한 "예고 없이 조정"이 이미 일어난 상태).
>
> **운영에는 문제없다** — 1일 1회를 쓰는데 20회가 있다. 달라지는 것은 **개발 중 여유**다.
>
> | 항목 | 영향 |
> |---|---|
> | 요약 실패 1건 | 재시도 2회 포함 **최대 3회 소모** |
> | 하루 실질 디버깅 횟수 | **6~7회** (20 ÷ 3) |
> | 프롬프트 개선용 10건 테스트 | 하루에 못 한다. **이틀로 나눌 것** |
>
> `ListModels` 같은 메타데이터 조회는 이 한도를 소모하지 않는다.

**🚨 반드시 지킬 것**

| 항목 | 내용 |
|---|---|
| 결제 비활성 유지 | <cite index="22-1">해당 프로젝트에 결제(billing)를 활성화하면 무료 티어가 사라지고 모든 호출이 첫 토큰부터 과금된다.</cite> 결제를 켜지 말 것 |
| 데이터 취급 | <cite index="25-1">무료 티어의 요청은 모델 개선에 사용될 수 있으므로</cite> 민감 정보를 보내지 않는다. 본 프로젝트는 공개된 뉴스 기사만 다루므로 문제없음 |
| 한도 변동 | <cite index="22-1">Google은 예고 없이 무료 한도를 조정한 전례가 있으므로</cite> 착수 시점에 AI Studio에서 실제 한도를 확인한다 |
| 모델 선택 | Pro 계열은 일일 한도가 가장 빡빡하므로 **Flash 계열 사용**. 단, 이름만 보고 고르지 말 것 — **AI Studio > 비율 제한에서 RPD가 `0 / 0`인 모델은 그 계정에서 쓸 수 없다** |
| 모델 단종 | 구형 모델은 `404 ... no longer available to new users`로 막힌다. 신규 계정에서 특히 잦으므로 **착수 시점에 실제 호출로 확인**한다 |
| 429 대응 | 한도 초과 시 429 오류 발생 → 재시도 간격을 두고 최대 2회 |

## 10. 에러 처리 정책

| 코드 | 상황 | 처리 | 재시도 | 선택 이유 |
|---|---|---|---|---|
| E-01 | RSS 응답 없음 / 타임아웃 | 재시도 후 실패 시 종료 + 로그 | 2회 (5분 간격) | 일시적 네트워크 장애가 대부분. 무한 재시도는 비용·한도 위험 |
| E-02 | RSS 파싱 실패 (형식 오류) | 즉시 종료 + 로그 | 0회 | 재시도해도 동일 결과. 피드 구조 변경은 사람이 확인해야 함 |
| E-03 | 키워드 매칭 0건 | **정상 스킵** 후 종료 | — | 오류가 아님. 그날 관련 뉴스가 없는 것은 정상 상황이며 알림 피로도를 유발하지 않아야 함 |
| E-04 | 중복 기사 (이미 저장됨) | **정상 스킵** 후 종료 | — | 오류가 아님. AI 호출 전 종료하여 비용 방어 |
| E-05 | Gemini API 429 (한도 초과) | 재시도 후 실패 시 요약 없이 저장 | 2회 (간격 증가) | 원문 링크라도 남겨야 수동 확인이 가능 |
| E-06 | Gemini API 기타 오류 | 재시도 후 실패 시 요약문에 `요약 실패` 기록하고 나머지 필드 저장 | 2회 | 데이터 유실 방지가 요약 품질보다 우선 |
| E-07 | Gemini 응답이 3줄 초과 | 앞 3줄만 잘라 저장 | 0회 | 재호출은 "기사당 1회" 원칙 위반. 후처리로 해결 |
| E-08 | 날짜 포맷 변환 실패 | 발행일시를 비우고 나머지 저장 + 로그 | 0회 | 부분 저장이 전체 실패보다 낫다 |
| E-09 | Notion 저장 실패 | 재시도 후 실패 시 종료 + 알림 | 2회 | 최종 산출물 유실이므로 알림 대상 |
| E-10 | 인증/권한 오류 | 즉시 종료 + 알림 | 0회 | 재시도로 해결되지 않는 설정 문제 |

**공통 원칙**
- 정상 스킵(E-03, E-04)은 알림을 보내지 않는다.
- 실제 장애(E-01, E-09, E-10)만 알림 대상으로 한다.
- 어떤 경우에도 시나리오가 자기 자신을 재트리거하지 않는다.
